# 핸드오프 — MAR/EOS AS-IS 치환 도구 (2026-08-18, 3차)

`2026-08-18b.md`의 `next`를 실행한 세션. **8/18b 미해결 1번(Find-AsisPath 스캔 경로 5.1 런타임 검증)을 종결**했다.
코드 변경은 하지 않았다 — 검증 통과 시점과 코드 변경 시점을 분리하기 위해 정리 3건은 다음 세션으로 미뤘다.

> 파일명 접미사 `c` — 같은 날 세 번째. `-2`/`-3`은 대시보드가 구버전을 집는다 (8/18b 상단 주석 참조).

## 오늘 확정한 것

### 1. Find-AsisPath v9.8 — PS 5.1 런타임 검증 통과

픽스처가 없어서 생성 스크립트(`New-FindTestFixture.ps1`)부터 만들었다.
컨테이너 PS 7.4에서 기준선을 뽑고, 형이 회사 PS 5.1에서 같은 픽스처로 재현한 리포트를 대조했다.

```
OS 의존 컬럼(RelPath, File) 제외 후 29행 전체 비교 → 완전일치
Kind / Action / Category / Ext / Entry / Line / Target / Value / Match  차이 0건
```

**`Line` 값까지 같다**는 게 핵심이다. 정규식 조립부와 `Kind`/`Target`/`Value` 컬럼 생성부가
5.1에서 실제로 실행됐고 7.4와 같은 판정을 냈다는 뜻이다.
8/18b에서 "배너만 떴을 뿐 본체는 한 줄도 안 돌았다"고 적어둔 나머지 절반이 닫혔다.

| 항목 | 결과 |
|---|---|
| 총 검출 | 29건 (path 8 / unc 8 / port 5 / ip 4 / domain 3 / host 1) |
| FoundIn | FILE 23 / CLASS 3 / JAR 3 — **세 경로 전부 실행됨** |
| `_skipped.dat` | 3행 (jar `commons-lang-2.6.jar` / domain `www.w3.org` / ip `127.0.0.1`) |
| 오탐 케이스 N01~N15 | 전부 0건 |
| `[C04]` 상수풀 길이바이트 0x2F | 0건 — v9.4 `//host/share` 기본 OFF 회귀 확인 |

**이 29건이 앞으로의 회귀 기준선이다.** 픽스처를 고치면 이 숫자도 같이 갱신할 것.

### 2. 픽스처 커버리지 설계 — `-Inventory`가 못 덮는 구간을 겨냥

| 구성 | 덮는 코드 경로 |
|---|---|
| `FindTest.java` (UTF-8 BOM) | P01~P05 / U01~U04 / I·T·D·H + **N01~N15 오탐 방지 케이스** |
| `findtest.properties` (ASCII) | `drive=T:` `nas=\\host` 의 '= 뒤 줄끝' 분기, `127.0.0.1` ExcludeIps 증적 |
| `Test.class` (합성) | 상수풀 UTF8 엔트리 흉내. **[C04]는 길이바이트를 일부러 0x2F(`/`)로** 만들어 `//uss` 가스 재현 |
| `eos-common-1.0.jar` / `commons-lang-2.6.jar` | 아카이브 스캔 + `-ExcludeJars` 제외 증적 |

`.class`는 JDK 없이 만들 수 있다 — Find는 `.class`를 파싱하지 않고 **ASCII 디코드 후 정규식만** 돌리므로
`0x01 + 2바이트 길이 + 바이트열` 형태만 흉내내면 충분하다 (588행).

> **한계 (8/18b 교훈 유지):** 합성 픽스처는 '이미 아는 케이스'만 재현한다.
> DOCTYPE 공개식별자도 상수풀 0x2F도 실측 리포트에서 처음 나왔다. **회귀 확인용이지 신규 오탐 발굴용이 아니다.**

### 3. Export-Csv BOM 버전차 — 추측에서 실측으로

8/18b의 표가 실물로 확인됐다.

| 산출 환경 | 리포트 선두 바이트 |
|---|---|
| 회사 PS 5.1 | `EF BB BF` (BOM 有) |
| 컨테이너 PS 7.4 | `22 46 6F` (`"Fo` — BOM 無) |

**회사에서 리포트를 만드는 한 안전하다**는 것도 같이 확인됐다. 급한 문제가 아니라는 근거다.

### 4. [신규] 아카이브·class 안 한글은 리포트에서 눈으로 못 본다

JAR 행 `Match`가 `# [J01] jar ??..` 로 나왔다. 픽스처 버그가 아니라 **Find의 설계**다.

```powershell
# 566행 (아카이브 엔트리)                    # 588행 (.class)
New-Object System.IO.StreamReader(           [System.Text.Encoding]::ASCII.GetString(
    $e.Open(), [System.Text.Encoding]::ASCII)    [System.IO.File]::ReadAllBytes(...))
```

바이너리 안전을 위한 올바른 선택이고, **탐지 패턴이 전부 ASCII라 검출 건수에는 영향이 없다.**
다만 jar/war/class 안 한글 리터럴은 `Match`/`Context` 컬럼으로 확인이 불가능하다.

**경계가 명확해진 것:** 아카이브 안 한글 확인은 A 계열(Find)이 아니라
**B 계열(`Expand-ArchivesForScan` + `Scan-ClassFiles`) 담당**이다. 두 축의 역할 분담 근거가 생겼다.

## 이어서 할 때 참고

- **검증 통과와 코드 변경을 같은 세션에 섞지 않는다.** 오늘 정리 3건을 같이 했으면
  "29건 기준선이 어느 버전 거였지"가 다음에 또 애매해진다. 8/12 "8개 클래스 vs 11개 클래스" 사고와 같은 형태다
- **픽스처는 기준선 숫자와 한 몸이다.** 케이스를 추가하면 `New-FindTestFixture` 콘솔 기대값도 같이 고칠 것.
  둘이 어긋나면 픽스처 자체를 못 믿게 된다
- **JDK 없이도 `.class` 픽스처를 만들 수 있다** — Find가 상수풀을 파싱하지 않기 때문.
  반대로 **B 계열(`Scan-ClassFiles`)은 진짜 파싱을 하므로 이 합성 class를 못 쓴다.** 거기엔 `Phase6-Invoke-ReproMatrix`(실제 javac)가 필요하다
- **아카이브/class의 `Match` 컬럼은 ASCII다.** jar 안 한글이 `?`로 보여도 검출은 정상이다.
  한글 내용 확인이 필요하면 B 계열로 넘길 것 — A 계열의 역할이 아니다
- `-Inventory`처럼 조기 `return`하는 모드로는 본체가 안 돈다 (8/18b). 이번 픽스처가 그 반대 사례 —
  **검증 수단을 고를 때 '그 수단이 어디까지 실행되는지'를 먼저 볼 것**
